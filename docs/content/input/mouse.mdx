Bubble Tea reports mouse events in screen coordinates. bloom knows where it drew every node, so you attach handlers
to the nodes themselves, and bloom runs the right one with positions relative to that node.

The [mouse example](https://github.com/lrstanley/bloom/tree/master/_examples/mouse) has hover styles, clicks and double clicks, wheel scrolling, and a divider you
can drag:

![The mouse example: a hover style following the pointer down a list, a click and a double click opening a file, the wheel scrolling it, and the divider dragged wider and narrower](/demos/mouse.webp)

## Mouse reporting

The view `m.ui.View` returns sets `MouseMode` to the least its frame needs, so you don't set it yourself:

- `tea.MouseModeAllMotion`, to get motion while no button is pressed, while a node has a [hover](#hover) style or an
  `on.Hover` handler, or a [tooltip](/input/tooltips) the pointer could open.
- `tea.MouseModeCellMotion`, which reports clicks, the wheel, and drags, while a node has other handlers, is
  [selectable](/input/selection), or can be focused with a click under [`WithFocus`](/input/focus).
- `tea.MouseModeNone` otherwise, which leaves the terminal's own selection working.

It's worked out again for every frame, so opening a dialog full of buttons turns reporting on, and closing it turns
it off. To ask for something else, such as to follow the pointer in `Update` yourself, set the mode on the view
before returning it:

```go
v := m.ui.View(m.width, m.height, layout)
v.MouseMode = tea.MouseModeAllMotion
return v
```

Asking for less than the frame needs takes away what needs it. Under `tea.MouseModeCellMotion` the terminal reports
the pointer only while a button is held, so hover styles and `on.Hover` don't follow it, and tooltips don't open
under it. Clicks, the wheel, drags, and keyboard [tooltips](/input/tooltips#reach-tooltips-from-the-keyboard) still
work.

## Attach handlers

Every node has an `On` method, which takes handlers made by the
[`on`](https://pkg.go.dev/bloomfx.dev/bloom/on) package:

```go
import "bloomfx.dev/bloom/on"
```

```go
for i, s := range services {
	rows[i] = bloom.Text(s).On(
		on.Click(func() tea.Cmd { m.selected = i; return nil }),
		on.DoubleClick(func() tea.Cmd { return m.open(i) }),
		on.RightClick(on.Msg(menuMsg{i})),
	)
}
```

No IDs are needed: the handler is already on the node it's about. Every kind of node has `On`, from text and
slots to boxes, rows, columns, layers, lists, and viewports.

| Handler | Runs on |
| --- | --- |
| `on.Click(fn)` | a left click: the button goes down and comes up over the node |
| `on.RightClick(fn)`, `on.MiddleClick(fn)` | a click with those buttons |
| `on.DoubleClick(fn)` | the second of two clicks within 400ms; both clicks still run `Click` |
| `on.Press(fn)` | a left click, or <kbd>enter</kbd> or <kbd>space</kbd> while the node has [focus](/input/focus#press-buttons-with-the-keyboard), through `m.focus.Update` |
| `on.ClickAt(fn)`, `on.RightClickAt(fn)` | a left or right click, with where the button came up |
| `on.Scroll(fn)` | the wheel, as `dx, dy` steps |
| `on.Hover(fn)` | the pointer moving onto the node (`true`) or off it (`false`) |
| `on.Drag(fn)` | the button going down on the node, the pointer moving while it's held, and it coming up |
| `on.ClickOutside(fn)` | a button going down anywhere but on the node |
| `on.Down(fn)` | a button going down on the node or anything in it, without waiting for it to come up, such as to bring a window to the front; it takes nothing from the nodes in it |
| `on.Mouse(fn)` | every mouse event over the node, for anything else |

Most take a `func() tea.Cmd`, so methods such as `m.save` can be passed as they are. Clicks run when the button
comes up over the same node it went down on, like a real button: pressing a button and sliding off it before
letting go doesn't click it.

Inside a [selectable](/input/selection) node, a click waits 400ms to see whether it becomes a double click, and a
double click selects a word instead of running `DoubleClick`. See
[Clicks and drags in selectable nodes](/input/selection#clicks-and-drags-in-selectable-nodes).

## Change state, or send a message

Handlers run on the Bubble Tea event loop, just before `Update` gets the same event, so a handler can change the
model directly, the same way `Update` does: change state, then return a command. The command runs in the
background, so a `tea.Tick` or I/O doesn't freeze the screen. Handlers themselves must not block.

A handler can only change the real model if it reaches it. Handlers are closures made in `View`, so they capture
whatever `View` had. With a pointer receiver, `func (m *model) View()`, that's the model itself. With a value
receiver, it's a copy, and changes made to it are lost without warning.

When a handler can't reach the state, have it send a message instead. `on.Msg(msg)` makes a handler function that
sends `msg` to `Update`:

```go
bloom.Text(name).On(on.Click(on.Msg(openMsg(i))))
```

```go
	case openMsg:
		m.page = int(msg)
```

<Callout type="warn" title="Components kept by value">
  This matters most for components. A Bubbles-style component is often kept by value in its parent
  (`m.list, cmd = m.list.Update(msg)`), so a handler built in its own `View` that sets `l.selected` changes a copy,
  even when the parent is a pointer. Have the component send a message with `on.Msg` and handle it in its own
  `Update`, give it pointer receivers, or build the handler in the parent over `&m.list`.
</Callout>

Messages from separate events can arrive in any order, since Bubble Tea sends each in its own goroutine. Changes
made directly in handlers happen in order.

## Which node gets the event

For each kind of event, the innermost node under the pointer with a handler for it takes it, and the nodes it's
inside don't. A row's `Click` and its pane's `Scroll` work side by side, with no need to stop anything from
spreading:

```go
pane := bloom.Column(rows...).On(on.Scroll(func(_, dy int) tea.Cmd { m.offset += dy * 3; return nil }))
```

A click on a row runs the row's `Click`; the wheel over the same row scrolls the pane. A click on the pane where
there's no row runs the pane's `Click`, if it has one. Gaps between the children of a row or column belong to the
row or column, so a click anywhere along a list row's line can select it.

Hover is the exception: every node under the pointer is hovered, as in CSS.

### Pass an event on

A handler that has no use for an event can return `on.Pass` instead of a command. The event then goes to the
nearest node around it with a handler for it, as though the inner node had none, and on outward until a
handler takes it. A cell with no menu of its own can leave a right click to its row:

```go
cell := bloom.Text(name).On(on.RightClick(func() tea.Cmd {
	if !m.hasMenu(i) {
		return on.Pass // the row's menu opens instead
	}
	return m.openMenu(i)
}))
row := bloom.Row(cells...).On(on.RightClickAt(m.rowMenu))
```

The handler that takes the event gets it relative to its own node, as though it had been the innermost. Return
`on.Pass` only when the handler changed nothing, since the handlers around it act on the event too.

`on.Pass` works for the handlers that send an event to one node: `Click`, `ClickAt`, `RightClick`, `RightClickAt`,
`MiddleClick`, `DoubleClick`, `Press`, `Scroll`, and `Mouse`. A `Press` run by <kbd>enter</kbd> or <kbd>space</kbd>
that passes leaves the key to your `Update`, as `m.focus.Update` reports it unhandled. A left click goes to the next
`Click`, `ClickAt`, or `Press`, whichever it is. `Hover`, `Down`, and `ClickOutside` already run for every node
they're on, and a drag stays with the node it started on: they take `on.Pass` as `nil`. Events never pass out of a
[modal layer](/layers/dialogs).

Return `on.Pass` as it is, like `tea.Quit`. `tea.Batch(on.Pass)` is still `on.Pass`, but batched with any other
command it's a command, and the handler takes the event.

Nodes made [selectable](/input/selection) take left-button drags to select their text, unless a node inside them
has an `on.Drag` handler.

## Use the position inside a node

`on.ClickAt` gets an [`on.Event`](https://pkg.go.dev/bloomfx.dev/bloom/on#Event), with `X` and `Y`
relative to the node the handler is on, and `W` and `H`, its size. A seek bar needs nothing else:

```go
bloom.Fixed(1, bar).On(on.ClickAt(func(e on.Event) tea.Cmd {
	m.position = m.duration * time.Duration(e.X) / time.Duration(e.W)
	return nil
}))
```

The rectangle of a box includes its border and padding, so `X` and `Y` count from its outer corner.

`e.Msg` is the original mouse message, for its modifier keys or button. It's nil when no mouse event caused the
run, such as a key pressing an `on.Press` handler.

## Scroll with the wheel

`on.Scroll` gets `dy` as `1` for each step down and `-1` for each step up, and `dx` the same for left and right.
Each pane scrolls on its own:

```go
bloom.Fill(m.reader).On(on.Scroll(func(_, dy int) tea.Cmd { m.offset += dy * 3; return nil }))
```

Clamp the offset in `Update`, which gets the wheel event after the handler ran.

### Scroll inside something that scrolls

A step that a handler [passes on](#pass-an-event-on) goes to the nearest node around it with an `on.Scroll`
handler, the way a browser hands the wheel from a box that can't scroll to the page. Return `on.Pass` when the
step would change nothing, such as when the cursor is already on the last item. Then the wheel over a field in a
form scrolls the form once the field can't move:

```go
bloom.List(len(m.items), m.row).Keep(m.cursor).On(on.Scroll(func(_, dy int) tea.Cmd {
	next := min(max(m.cursor+dy, 0), len(m.items)-1)
	if next == m.cursor {
		return on.Pass // the form around the list scrolls instead
	}
	m.cursor = next
	return nil
}))
```

A [viewport](/content/viewports)'s `OnScroll` does this on its own: a step at its edge, or with all its text in
sight, goes to what the viewport is in. So a one-line input can keep its `OnScroll`, and the wheel over it scrolls
the form. Each axis is judged on its own, so an input with a line too long to show still scrolls sideways.

A handler with nothing around it to pass steps to, such as the form's, can take every step and clamp in `Update`
as above.

Each step is judged on its own, even within a quick turn of the wheel, so a turn that takes a viewport to its end
carries on into what it's in.

## Hover

[`HoverStyle`](https://pkg.go.dev/bloomfx.dev/bloom#TextNode.HoverStyle) on text and boxes swaps in a style while the pointer is over the node, with no state in the model:

```go
bloom.Text("save").Style(button).HoverStyle(buttonHover).On(on.Press(m.save))
```

Give it a style that takes the same space as the node's own, changing only its colors and attributes.

For a tooltip, use the [built-in ones](/input/tooltips): `Tooltip("Deploy")` on the node, with no state in the
model. For anything more, `on.Hover` runs when the pointer moves onto the node and off it:

```go
bloom.Text("deploy").On(on.Hover(func(over bool) tea.Cmd { m.preview = over; return nil }))
```

Hover styles and `on.Hover` make the view report all motion, to follow the pointer while no button is down.

A node stops being hovered when something covers it, such as a dialog opening over it, even without the pointer
moving. bloom notices on the next message `m.ui.Update` gets after the frame is drawn, such as an animation frame, a
key, or the pointer moving. Terminals don't report the pointer leaving the window, so the hover also ends when the
window loses focus, which needs `v.ReportFocus = true`.

## Drag

`on.Drag` runs when the left button goes down on the node, each time the pointer moves while it's held, and once
more with `Done` set when it comes up. The node keeps getting the drag after the pointer leaves it, which a
one-cell splitter needs:

```go
divider := bloom.Fixed(1, bloom.Text("│")).On(on.Drag(func(e on.Event) tea.Cmd {
	m.split = e.Screen.X
	return nil
}))
```

`e.Screen` is where the pointer is on screen, `e.Start` is where the drag started, and `e.X` and `e.Y` are relative
to the node, outside it when the pointer is.

A drag also ends, with `Done` set, when the node leaves the frame or a modal layer opens over it, and when the
release gets lost, such as outside the window. bloom follows the dragged node from frame to frame by its ID, or
without one, by where it is in the nearest node with an ID around it, or in the whole tree when there's none. Give a
node that moves around in the tree while it's dragged an ID, or put it in one that has one: the title bar of a
window whose layer has an ID stays the same node as the window is brought to the front.

To drag something that moves, such as a window by its title bar, remember where it was when the button went down,
and move it by as much as the pointer has moved since, `e.Screen.Sub(e.Start)`. The
[desktop example](https://github.com/lrstanley/bloom/tree/master/_examples/desktop) moves and resizes windows that
way, and they stay where they're dropped because where each one is lives in the model.

`Place` puts the layer at a rectangle the model keeps, and `on.Down` brings the window to the front as soon as the
button goes down on it, without taking the click from its buttons or the drag from its title bar. For a window that
[animates](/motion/layout-animation) to follow the pointer cell for cell, leave `Animate` off while it's dragged. Once it's back, the window carries on from where it was dropped, so one let go against an edge glides
into the place it snaps to:

```go
layer := bloom.Layer(window).ID(windowID).Place(m.rect).On(on.Down(m.raise))
if !m.dragging {
	layer = layer.Animate(anim.Spring(22, 1))
}
```

## Layers and the mouse

Layers drawn on top get events first. A layer that's [modal](/layers/dialogs#make-it-modal) takes every event from
what's beneath it. `on.ClickOutside` on a modal layer runs for a click on its backdrop, which is how a dialog closes
when you click away from it:

```go
bloom.Layer(dialog).Modal().On(on.ClickOutside(m.closeDialog))
```

On a layer that isn't modal, such as a [dropdown](/layers/dropdowns), `on.ClickOutside` runs for a click anywhere
else, and the click still reaches what it's on.

A layer whose presence is hidden doesn't take events. One that's still animating out does, so a modal dialog keeps
blocking clicks until it's gone.

## Handle raw events yourself

The original `tea.MouseClickMsg` and the other mouse messages still reach `Update`. If you handle them as well as
using handlers, don't act on the same event twice. To find what's under a point, [`m.ui.Frame().Hit(x, y)`](https://pkg.go.dev/bloomfx.dev/bloom#Frame.Hit) returns
the IDs of the nodes there, outermost first. See [IDs](/concepts/how-a-program-runs#ids) for when a node needs one:

```go
	case tea.MouseClickMsg:
		if path := m.ui.Frame().Hit(msg.X, msg.Y); slices.Contains(path, paneLog) {
			m.follow = false
		}
```

For things other than events, such as drawing an effect from a button's position, `m.ui.Frame().Rect(id)` returns
where a node was drawn in the last frame, in screen coordinates (see
[Sizes and positions in Update](/bubble-tea/sizes-in-update)):

```go
if r, ok := m.ui.Frame().Rect(buttonDeploy); ok {
	center := image.Pt((r.Min.X+r.Max.X)/2, (r.Min.Y+r.Max.Y)/2)
	// ...
}
```

## Fewer frames for the mouse

Terminals can send wheel and motion events faster than they're worth drawing. [`bloom.ThrottleMouse`](https://pkg.go.dev/bloomfx.dev/bloom#ThrottleMouse) makes a
Bubble Tea filter that drops those that come too soon after the last:

```go
p := tea.NewProgram(m, tea.WithFilter(bloom.ThrottleMouse(15*time.Millisecond)))
```

A dropped event isn't made up for: the wheel scrolls a little less, and if the pointer stops right after a dropped
motion event, hover catches up when it moves again.

## How it works

`m.ui.View` installs a `tea.View.OnMouse` handler. Bubble Tea calls it on its event loop for each mouse event,
before `Update` and the next `View`, which is what lets handlers change the model safely and have the change drawn
right away. bloom runs the handlers there, and batches the commands they return, which Bubble Tea then runs in the
background like any other.

Bubble Tea routes each event with the view it painted last, so the handlers that run are those of the frame on
screen. It can keep that view over a newer one with the same content, so when the latest frame draws the same,
bloom routes with it instead, and handlers and tooltips that changed without changing what's drawn take effect on
the next event.

If the view doesn't come from `m.ui.View`, or something replaces its `OnMouse`, `m.ui.Update` runs the handlers
instead when it gets the event, so pass it every message. It skips events that `OnMouse` already handled.

## Test handlers

[`m.ui.Click(id)`](https://pkg.go.dev/bloomfx.dev/bloom#Root.Click) clicks the middle of the node with an ID, and `m.ui.ClickAt(x, y)` clicks a point, running the
handlers of the last frame drawn and returning their commands. `m.ui.Update` runs handlers for any other mouse
message, so a test can drive hover, the wheel, and drags without a terminal:

```go
m.View()
m.ui.Update(tea.MouseMotionMsg{X: 3, Y: 1})
if _, ok := m.ui.Click(buttonSave); !ok || m.saves != 1 {
	t.Fatal("save was not pressed")
}
```
