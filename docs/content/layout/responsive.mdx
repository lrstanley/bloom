---

Terminal windows range from a narrow split pane to a full-screen monitor. bloom gives you three tools to adapt:
collapsing panels when they don't fit, percentages, and components that build a different layout for the space
they get. Below the size where nothing adapts any further, it can show a note that the window is too small.

The [responsive example](https://github.com/lrstanley/bloom/tree/master/_examples/responsive) uses all of them as the terminal narrows and widens again:

![The responsive example: paging and scrolling the reader, then the toolbar dropping its labels, the details panel, and the navigation as the terminal narrows, and a note that the window is too small below the reader's minimum](/demos/responsive.webp)

## Collapse panels when space runs out

Mark slots `Collapsible(priority)` and set the `Min` of the slots that must stay usable. When the minimum sizes
don't all fit, bloom drops collapsible slots, lowest priority first, along with the gap beside each.

```go
bloom.Row(
	bloom.Fixed(24, nav).Collapsible(2),
	bloom.Fill(reader).Min(40),
	bloom.Fixed(30, details).Collapsible(1),
)
```

As the terminal narrows below 94 columns, the details panel goes first because its priority is lowest. Below
64 columns, the navigation goes too, and the reader has the whole width. Widen the terminal and they come back.

A collapsed slot isn't drawn and has no rectangle, so `frame.Rect(id)` reports `false` for it. You can use that to
show a hint, such as a key to open the missing panel.

## Size by percentage

`Percent(p, c)` gives a child `p` percent of its container, which keeps proportions as the terminal resizes:

```go
bloom.Row(
	bloom.Percent(30, list),
	bloom.Fill(preview),
)
```

Unlike `Fixed`, a percentage slot can shrink below its share when space runs short, down to its `Min`.

## Build a layout for the space you're given

Some components should change shape, not just size: a toolbar that shows icon labels when wide and only icons
when narrow, or a form that's two columns on a wide screen and one on a narrow one.

A component that implements [`bloom.Layouter`](https://pkg.go.dev/bloomfx.dev/bloom#Layouter) builds its
own layout. bloom calls its `Layout` method with a `bloom.Context` holding the width and height it has, and draws
whatever it returns:

```go
type toolbar struct {
	actions []string
}

// View is used when the toolbar is drawn on its own, outside a bloom layout.
func (t toolbar) View() string {
	return strings.Join(t.actions, " ")
}

func (t toolbar) Layout(ctx bloom.Context) bloom.Child {
	children := []bloom.Child{bloom.Text("◆ reader"), bloom.Space()}
	for _, action := range t.actions {
		if ctx.Width < 70 {
			// "⟳ refresh" becomes "⟳".
			action, _, _ = strings.Cut(action, " ")
		}
		children = append(children, bloom.Text(action).Style(actionStyle))
	}
	return bloom.Row(children...)
}
```

`Layout` may be called more than once a frame, while bloom measures as well as for the final layout, so it must
not change the component. Treat it like `View`: read state, return nodes.

## Switch between a row and a column

The same idea works for a whole screen. A `Layouter` can return a row on a wide terminal and a column on a
narrow one:

```go
type editor struct {
	code, preview bloom.Child
}

func (e editor) View() string {
	return bloom.Render(0, 0, e.Layout(bloom.Context{}))
}

func (e editor) Layout(ctx bloom.Context) bloom.Child {
	if ctx.Width >= 100 {
		return bloom.Row(bloom.Fill(e.code), bloom.Fill(e.preview)).Gap(1)
	}
	return bloom.Column(bloom.Fill(e.code), bloom.Fill(e.preview))
}
```

`bloom.Render` with a size of zero draws a layout at its natural size, which gives the component a sensible
`View` when it's used outside a bloom layout.

## Show a note when the window is too small

Some layouts can't be used below a certain size, however much collapses. Wrap the root of the layout in
`MinSize(w, h, child)`, and in a smaller window bloom draws one line in its place, centered, and faded toward the
terminal's background:

```go
func (m *model) View() tea.View {
	return m.ui.View(m.width, m.height, bloom.MinSize(80, 24, m.layout()))
}
```

```
window too small, min 80x24
```

A width or height of zero has no minimum on that axis, and the note says only what's needed, such as
`min 80w`. In a window too narrow for the whole line, it says only `window too small`.

While the note is on screen the layout isn't drawn, so its mouse handlers don't run and focus skips its nodes.
Keys still reach `Update`. Compare the window's size with the minimum to ignore the keys that would change a
layout no one can see:

```go
case tea.KeyPressMsg:
	if m.width < 80 || m.height < 24 {
		break
	}
```

Because the minimum is part of the tree, it can change from frame to frame, such as by page, and `MinSize` can
wrap a single panel as well as the whole screen. Where it fits, its natural size is at least its minimum, so in
an `Auto` slot, or drawn at its natural height, it's given that much.

For a note of your own, check the size yourself and return it from your layout in place of the rest.
